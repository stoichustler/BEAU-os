# ISO 26262 C Coding Rules

This document records the C coding rules used by BEAU OS for safety-oriented
implementation and review. It is a project guideline derived from ISO 26262
software-unit implementation and verification principles, not a replacement for
the ISO 26262 standard text.

## Scope

These rules apply to BEAU OS C code in:

- `arch/`
- `core/`
- `include/`
- `sdk/bsp/`

Third-party imported code keeps its upstream style unless BEAU modifies the
logic. Modified third-party files should follow these rules for the changed
area.

## General Principles

1. Every safety-relevant code path must have a deterministic result for invalid
   input, resource exhaustion, timeout, and ownership conflict.
2. Isolation failures must fail closed. Do not expose memory, IRQs, DMA streams,
   MMIO windows, or device ownership before all validation and synchronization
   steps have succeeded.
3. Do not rely on undefined, unspecified, or implementation-defined C behavior
   unless it is wrapped by a documented architecture helper.
4. Prefer explicit state transitions over implicit side effects.
5. Runtime diagnostics must identify the object, owner, and failing condition
   where practical, for example VM ID, vCPU ID, StreamID, BDF, IRQ, GPA/IPA, or
   state name.

## Required C Rules

### Control Flow

- Keep functions single-purpose and bounded in complexity.
- Avoid hidden fall-through in `switch`. Use explicit `break`, `return`, or a
  clearly marked fall-through helper when intentional.
- Always handle `default` in externally controlled enum or integer switches.
- Avoid recursion in hypervisor code.
- Avoid unbounded loops. Loops that wait for hardware must have a timeout or
  retry limit.
- Do not ignore return values from functions that validate, allocate, map,
  lock, copy, or publish ownership.

### Data And Initialization

- Initialize all automatic variables before use.
- Initialize all structure fields that cross subsystem, VM, or hardware
  boundaries.
- Prefer fixed-width integer types for hardware registers, ABI structures, MMIO,
  device-tree data, and guest-visible data.
- Keep ABI structures layout-stable. Changes require versioning or explicit
  compatibility handling.
- Do not use magic numbers in logic. Define named constants for register fields,
  limits, sizes, states, and timeouts.
- Use compile-time assertions for ABI sizes, alignment, array bounds, and
  hardware descriptor layouts.

### Integer Safety

- Validate size, offset, count, and index before arithmetic.
- Check addition and multiplication for overflow before using the result as an
  address, size, allocation length, array index, or MMIO offset.
- Do not mix signed and unsigned values in range checks unless the conversion is
  intentional and local.
- Do not truncate address, size, or register values without an explicit range
  check.
- Use bit masks and shifts only with validated shift widths.

### Pointer And Memory Safety

- Check all external pointers before dereference unless the caller contract is
  enforced by an immediately visible assertion.
- Do not keep stale pointers after ownership transfer or teardown.
- Clear pointers after release when later code can observe the object again.
- Do not copy from guest memory, device-tree data, ACPI tables, or firmware
  tables without validating size and range first.
- Use bounded string and memory operations.
- Do not expose partially initialized objects to global lists, VM state, IRQ
  routing, or device ownership tables.

### Concurrency And Ordering

- Document the owner of shared state: pCPU-local, VM-local, global, IRQ context,
  or hardware-owned.
- Protect shared mutable state with the matching lock or atomic primitive.
- Keep lock ordering deterministic and avoid nested locks unless the order is
  documented near the code.
- Do not call blocking or long-running code while holding spinlocks.
- Use memory barriers or cache maintenance when publishing data to hardware,
  other CPUs, guests, or DMA engines.
- Publish software ownership only after hardware state is synchronized.

### Hardware, MMIO, IRQ, And DMA

- Validate MMIO access width, alignment, offset, and direction.
- Mask reserved register bits and reject unsupported writes when emulating
  hardware.
- Map device memory with device attributes, not normal cacheable attributes.
- Program interrupt routing only after the target VM and virtual interrupt are
  valid.
- Program DMA ownership only after SMMU/IOMMU domain, StreamID, stage-2 root,
  and command synchronization have succeeded.
- Deassign devices in reverse order: stop guest visibility, quiesce interrupts,
  revoke DMA, then release software ownership.

### Error Handling

- Return a negative error code on failure and avoid silent success.
- Use one cleanup path for multi-step initialization when it improves
  determinism.
- Cleanup must undo only resources acquired by the current function or clearly
  owned by the current state transition.
- Error logs should be actionable and include the failing object identity.
- Fatal paths must be reserved for unrecoverable isolation or platform
  consistency violations.

### Comments

- Comments must explain design intent, ownership, ordering, isolation, and
  failure handling.
- Do not add comments that restate function names, assignments, or branch
  conditions.
- For non-trivial C design comments, use the project style in `sdk/sdk.md`:

```c
/* [YYYYmmDD] Topic
 *
 * compact ASCII diagram or state flow
 *
 * Key rule:
 *   - what owns the state;
 *   - what must happen before/after;
 *   - what failure is prevented.
 */
```

## Prohibited Patterns

- Undefined behavior, such as invalid shifts, signed overflow, use after free,
  out-of-bounds access, or uninitialized reads.
- Dynamic memory allocation in late runtime paths unless failure is handled
  deterministically.
- Hidden global state changes from helper functions.
- Publishing VM/device/IRQ ownership before all required validation succeeds.
- Direct guest, firmware, or hardware data trust without validation.
- Empty `else`, empty `default`, or ignored error paths.
- TODO/FIXME/XXX comments without a tracked owner and safety impact. Prefer
  either fixing the issue or documenting the concrete limitation in design
  terms.

## Code Review Checklist

Reviewers should check each C change for:

- External input validation: guest memory, HVC parameters, MMIO, PCI config,
  device tree, ACPI, firmware tables, and hardware registers.
- Boundary checks: array index, offset, size, count, address range, and integer
  overflow.
- Ownership ordering: object is not visible before initialization and is not
  reused after teardown.
- Isolation ordering: stage-2, SMMU/IOMMU, vGIC/ITS, vPCI, console, watchdog,
  and virtio ownership transitions fail closed.
- Locking: shared state has a clear owner and matching lock or atomic rule.
- Cleanup: every failure path releases only what it acquired.
- Diagnostics: logs are useful in field debug without leaking unrelated state.
- Comments: design comments explain why the ordering and ownership are safe.
- Tests: unit, smoke, or platform validation covers success and at least one
  failure path for safety-relevant behavior.
